## 3. 站規與停權風險（Q1）

- 條文：全站站規與 Gossiping／Stock／Tech_Job 板規都沒找到禁止自動化程式的條文；甲方沒有讀原文，內容是鏡像站轉述，所以是**未確認**，不是「沒有禁止」。細節與連結見 `docs/research/bbs-rules.md`。
- 唯一相關：SYSOP 2026-08-24 公告，稱「許多連線APP因自動連續登入連線，反而會被目前測試之功能阻斷登入」，自動連續登入有被阻斷的風險。第三方轉述稱短時間多次重連可能被當異常而暫時鎖定（可信度低）。
- 實驗中：登入共 2 次（P0 一次、P1＋P2 一次，間隔約 13 分鐘），皆成功；沒有警告、沒有觸發立即停止；小號沒有被停權（甲方回報）。2 次登入不足以推論長時間常駐的風險。
- IP：實驗所用的網路類型沒有記錄；沒有觀察到網頁版爬蟲被連帶影響（尾段網頁版 1 次 FetchError，原因未查，未驗證與 BBS 有關）。

## 4. 連線與分工（Q2、D 表、Q6）

- 同時登入數：只實測 1 條（D-044）；「3 條」是第三方說法，**未證實**。
- 容量口徑：採 P2 平均讀取 7.1 秒（61 次；即 `summary.json` 的 `avg_read_seconds`），因為導入時就是多篇輪流讀；`N_max` = ⌊120 ÷ (7.1 + 22.5)⌋ = 4，第 1 節的 9 條與混合方案 N=4 都用這個口徑。全程 81 次平均是 7.9 秒（P1 10.2、P2 7.1），用它則 `N_max`=3、需 11 條、混合 N=3。`summary.json` 的 `avg_sends`（8.8）是 81 次平均，與 `avg_read_seconds` 口徑不一致，屬 `tools/bbs_spike.py` 的問題，這張單不改。同時熱門篇數（`bbs-hot-articles-stat`，11-01～11-06）p50 21、p90 33、最大 48。
- 讀取成本隨推文數變動：575～764 則的第 1 篇平均 10.7 秒、11.6 次；65～97 則的另兩篇約 5 秒、6 次。熱門文章越長越慢，`N_max` 實際會偏小。

## 6. 資料對應（Q5、E 表）

比對方式：BBS 事件與網頁版事件共用同一個辨識鍵（type、user_id、正規化 content、分鐘、同鍵第幾個），224 個 BBS 鍵在網頁版全部找到。

| 欄位 | 結果 |
|---|---|
| `floor` | 未驗證（事件檔只存鍵，沒有樓層）；PyPtt 每次讀到文末，可依序編號，讀到的推文數隨時間單調增加（575→764） |
| `type`、`user_id`、`content` | 一致：224/224 配對成功，不一致比例 0%（鍵含這三項） |
| `commented_at` | 一致：分鐘相同（鍵含分鐘）；`time_unparsed` = 0（81 次讀取），可用 `parse_comment_time` 的格式（P0 time_sample 為遮罩格式 `MM/DD HH:mm`）；年份推算沿用既有函式 |
| `ip` | P0 有；格式與網頁版沒有逐則比對，未驗證 |
| `post_id` | 通過：URL → AID → `get_post` 回傳的 URL 一致（P0 `aid_ok`）；檔名可還原 |
| `author`、`title`、`content`、`created_at` | 未驗證（事件檔不存）；讀取成本見第 4 節，只補推文做不到 `RawPost` 必填欄位 |
| `is_deleted` | 未驗證（實驗中沒遇到刪文） |
| `task_id` | 不適用 BBS 輪詢；建議由服務產生 UUID（不改 schema） |

衝突（7.31 E，讀程式推得，這版未實測）：快照語意與快照新舊兩項照舊；網頁版快取比 BBS 慢約 4 分鐘，實測支持了「網頁版較舊快照蓋掉 BBS 資料」的風險。解法：BBS 追蹤中的文章停止網頁版重爬，BBS 服務累積完整快照再送 `raw.posts`。
