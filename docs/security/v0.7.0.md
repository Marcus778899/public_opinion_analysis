### 0.2 L-5（#120）是否修好：**已修正**

判斷依據：

1. **編碼後的字元不可能離開字串**。Grafana 的 `percentencode` 是 `encodeURIComponent` 再加編 `!'()*`；多選值先包成 `{a,b}` 再整串編碼。輸出只會有 `A-Za-z0-9-_.~%`，沒有 `'`、`\`、空白、`$`。ClickHouse 單引號字串內只有 `'` 與 `\` 有特殊意義，`%` 沒有，所以任何網址值（`var-board`、`var-min_score`）都只能成為字串字面值的內容，無法結束字串，也無法造出 `$__` 讓 plugin 後端再展開巨集

## 3. 本次新列的發現

### M-4（medium）範例密碼 `change-me` 不會被擋，Grafana admin 與唯讀帳號可能用公開的預設密碼上線

**位置**
- `.env.example:67`（`CLICKHOUSE_GRAFANA_PASSWORD`）、`.env.example:71`（`GRAFANA_ADMIN_PASSWORD`）：範例值是小寫 `change-me`
- `scripts/check_env.py:28`、`:82`：只把含大寫 `CHANGE_ME` 的值當「還沒填」，`change-me` 會被當成已填，`check_env` 回報「設定齊全」
- `infra/docker-compose.yaml:367`：`${GRAFANA_ADMIN_PASSWORD:?}` 只擋空值，不擋範例值
- 開發規格 7.25 說「不設預設帳密」、README 寫「不可用 `change-me`」，但沒有任何程式檢查

**攻擊情境**：甲方照 README 跑 `check_env.py`，它從 `.env.example` 複製出 `.env` 並列出缺的值；兩個 Grafana 密碼不在清單裡，甲方沒改就 `make up`。Grafana 只綁 `127.0.0.1`，但瀏覽器能連：
1. 甲方用同一台機器瀏覽惡意網頁，網頁以 DNS rebinding 把自己的網域指到 `127.0.0.1:${GRAFANA_PORT}`。此時請求對 Grafana 而言是同源，Grafana 預設不檢查 Host（`enforce_domain` 預設關）
2. 頁面用公開的帳號 admin 與 `.env.example` 裡的密碼登入，透過 `/api/ds/query` 以唯讀帳號查 `radar` DB，把結果送回攻擊者；也能新增 datasource、改 Grafana 設定
3. 同一台機器上的其他本機使用者、程序也能直接登入

**能拿到什麼**：`radar` DB 的全部內容（PTT 公開資料、情緒推論、警示），以及 Grafana 的管理權限。唯讀帳號擋住寫入與 named collection，所以拿不到 Kafka 設定、也改不了資料。

**嚴重度理由**：需要「沒改範例密碼」加上「瀏覽到針對這個 port 的 DNS rebinding 網頁」或本機存取，資料大多是公開的 PTT 內容 → medium，不擋發版。同一個 `check_env` 漏洞也讓既有的 `POSTGRES_PASSWORD`、`CLICKHOUSE_PASSWORD`（`.env.example:38`、`:64`）的 `change-me` 不會被擋，那兩個帳號權限更大（ClickHouse 的 8123 也是 HTTP，同樣能被 DNS rebinding 打到），一起修。

**修法**
- `.env.example` 要甲方決定的密碼改成範本規定的 `CHANGE_ME`（`.claude/agents/architect.md` 的規範）；或 `check_env.py` 的比對改成不分大小寫、`-`／`_` 視為相同（`check_env.py` 屬上游範本，依 D-008 由甲方處理）
- Grafana 的 `GF_SECURITY_ADMIN_PASSWORD` 只在 `grafana_data` 第一次初始化時生效：已經用 `change-me` 啟動過的環境，改 `.env` 不會換掉密碼，README 要寫明改密碼的方式（`grafana cli admin reset-admin-password` 或 `down -v` 重建 volume）
- 補靜態測試：`.env.example` 的密碼類變數都要被 `check_env` 判為「還沒填」

- 改寫後的查詢可以讓 `url` 欄回傳任意網址，表格「開啟原文」就連到釣魚網站，繞過 7.25 威脅表「連結限 `https://www.ptt.cc/` 開頭」的對策（這個對策只過濾資料庫裡的 `posts.url`，沒擋住從變數注入的值）。`javascript:` 會被 Grafana 的 URL sanitize 擋下
- 查詢以唯讀帳號執行：不能寫入、不能讀其他 DB、`max_execution_time` 60 秒與記憶體 2 GB 上限，所以只能讀 `radar` 的資料、顯示在受害者自己的畫面上
- 若唯讀帳號能用 `url()` 等 table function（未實測，見「未涵蓋」），注入的查詢就能在受害者開網址的當下由 ClickHouse 主動把資料送到外部，不需要受害者再點擊；這是本項要補測試的原因

**嚴重度理由**：需要受害者已登入只綁本機的 Grafana、並開啟攻擊者給的網址，結果是釣魚連結或資源消耗（上限已設），資料本身受害者原本就看得到 → low。

**修法**
- `min_score` 改成 `custom` 變數，固定選項（例 0、0.3、0.5、0.7、0.9），Grafana 只接受清單內的值；或 SQL 改用 `${min_score:sqlstring}`（Grafana 會跳脫單引號），並保留 `toFloat64OrDefault`
- `$board` 改用 `${board:sqlstring}` 或 `${board:singlequote}`，不要依賴 plugin 的預設格式
- 補測試：`test_grafana_infra.py` 加 `test_readonly_user_cannot_use_table_functions`（`url`、`remote`、`file`、`s3`、`postgresql` 都要失敗）；`test_panels.py` 加「`min_score` 含單引號時查詢不會被改寫」
- uat 在真畫面用 `var-min_score`、`var-board` 帶單引號確認（已在 uat S8、S10 的未測項目裡）

### L-6（low）允許清單只擋指令，不擋推送

**位置**
- `src/radar/bot/main.py:103-115`：`is_allowed` 只用在 `handle_update`（指令與按鈕）
- `src/radar/bot/main.py:248-250`、`src/radar/bot/repository.py:114-126`：推送對象 `recipients` 只看 `subscriptions`、`chat_settings`，不看允許清單

**攻擊情境**：v0.6.0 預設 fail open，任何 Telegram 使用者都能 `/sub` 訂閱看板。升級到 v0.7.0 後甲方設好 `TELEGRAM_ALLOWED_CHAT_IDS`，以為 bot 只服務自己，但那些陌生 chat 的訂閱還在 PG，之後每則警示仍推給他們；而他們的 `/unsub` 會被允許清單擋掉、沒有回應，只能封鎖 bot（觸發 `forget_blocked_chat`）才會停止。

**能拿到什麼**：持續收到警示內容（PTT 公開資料的熱度與情緒），也讓 bot 對外的流量與 Telegram 送訊額度被不相干的 chat 佔用。

**嚴重度理由**：內容是公開資料加推論結果，沒有他人的個資或機密 → low。

**修法**：`recipients` 在 `allow_all` 為 false 時以 `Subscription.chat_id IN allowed_chat_ids` 過濾；或在 `check_allowlist` 通過後，清掉不在清單內的 chat 的訂閱與設定（不可逆，要先問甲方，屬決策分級 ④）。補測試 `test_notify_skips_subscribed_chat_not_in_allowlist`。
