## 發現

### M-1（medium）作者可改的文章標頭時間決定補抓終點：任何 PTT 使用者發一篇標頭時間在未來的文章，就能長期關掉該看板的停機補抓

- 位置
  - `src/radar/collector/parsers/ptt.py:100`：`posts.created_at` 優先取文章標頭的「時間」，沒有上限，`2099` 年也接受
  - `src/radar/collector/scheduler.py:102-120`：`since = max(posts.created_at) - 10 分鐘`，不排除未來時間
  - `src/radar/collector/crawler.py:124-133`：第一頁最舊文章（檔名時間，PTT 產生）`<= since` 就停止往前翻
- 攻擊情境：被追蹤看板上任何一個 PTT 帳號發文後，用 PTT 的編輯功能把標頭「時間」改成 `Fri Dec 31 23:59:00 2099`（開發規格 7.28 A 的「自行決定」表本身就寫了「作者可改」）。下一次重爬把 `created_at = 2099-12-31` 寫進 PG，從此 Scheduler 對這個看板送出的每個列表任務都帶 `since ≈ 2099`，爬蟲讀完第一頁就停，不送續抓任務，也不記任何 WARNING／ERROR（流程看起來正常）
- 能拿到什麼：#180 要修的問題原樣回來，而且是永久、無聲的：停機、休眠、Kafka 停擺之後，第一頁以前的文章都不補（7.29 估計 Gossiping 停機一天約漏 790 篇）。對輿情雷達而言，等於攻擊者能選擇性讓某個看板在故障後的資料出現缺口，Dashboard 與熱度偵測看不到那段期間。只要文章不被刪就一直有效
- 為什麼不是 high：不洩漏資料、不取得權限；只有在停機或積壓超過一頁時才有實際缺口；不過門檻只是一個 PTT 帳號，所以評 medium
- 修法（擇一，建議第一個）
  - `latest_post_since` 改用 PTT 產生的檔名時間：`post_id` 已含 `M.<epoch>`，可以查該看板 `post_id` 的最大 epoch（或加一個不可被作者改的欄位）；7.28 A「列表用檔名時間」的比較基準也就一致了
  - 至少在查詢加 `Post.created_at <= now`（或在 parser 把標頭時間限制在「檔名時間 ± 1 天」，超出就退回檔名時間，同 #211 對推文時間的做法）
  - 補測試：PG 有一篇 `created_at` 在未來的文章時，`since` 不會晚於現在
- 備註：同一個標頭時間也被拿來推算推文年份（`_bounded_comment_time`），但只影響攻擊者自己那篇文章的推文，#211 已把未來時間設為 `None`，不另列

### L-1（low）已初始化過的 Grafana volume 不會跟著 `.env` 換掉 admin 密碼，`secret-check` 通過但實際密碼仍是 `change-me`

- 位置：`infra/docker-compose.yaml:413`（`GF_SECURITY_ADMIN_PASSWORD` 只在 `grafana_data` 第一次初始化時生效）；README 與開發規格 7.25 沒有寫換密碼的方法
- 攻擊情境：v0.7.0、v0.8.0 時 `.env` 沿用 `change-me` 啟動過的環境，升到 v0.8.1 時 `secret-check` 擋下，甲方把 `.env` 改成新密碼後重新 `make up`，檢查通過；但 Grafana 的 admin 密碼存在 volume 的 `grafana.db` 裡，仍是 `change-me`。之後就是 v0.7.0 M-4 的情境：本機其他使用者，或甲方瀏覽的惡意網頁用 DNS rebinding 打 `127.0.0.1:${GRAFANA_PORT}`，用 `admin`／`change-me` 登入，查 `radar` DB、改 Grafana 設定
- 其他三個密碼不受影響：`CLICKHOUSE_PASSWORD` 由 image entrypoint 每次啟動寫入，`grafana.xml` 用 `from_env`；`POSTGRES_PASSWORD` 若沒同步，app 會連不上，甲方會發現
- 修法：README 第 1 步加一句「曾用 `change-me` 啟動過 Grafana 的環境，改完 `.env` 後要執行 `docker compose … exec grafana grafana cli admin reset-admin-password "$GRAFANA_ADMIN_PASSWORD"`（或刪掉 `grafana_data` 重建）」；或 compose 加一個一次性步驟每次啟動都重設 admin 密碼。這是 v0.7.0 M-4 修法清單的第二項，本版沒做

### L-2（low，v0.8.0 L-3 延續）`import_model` 的整包雜湊比對是選填，README 的步驟沒有用它

- 位置：`src/radar/ml/training/import_model.py:90-96`、`main()` 的 `--sha256`（選填）；README 階段 8 第 3 步
- 現況：v0.8.0 建議 `--sha256` 必填，本版做成選填並一律印出實際雜湊。擋替換仍靠甲方記得帶參數或手動對照。攻擊情境與 v0.8.0 相同（要先能改甲方下載資料夾的檔案，門檻高；ONNX 載入不會執行程式）
- 修法：README 第 3 步改成 `import_model --zip <路徑> --sha256 <notebook 印出的值>`；要不要改成必填由 manager 判斷

### 觀察（不列為發現）
