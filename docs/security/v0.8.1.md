## 發現

### M-1（medium）作者可改的文章標頭時間決定補抓終點：任何 PTT 使用者發一篇標頭時間在未來的文章，就能長期關掉該看板的停機補抓

- 追蹤：#268（OPEN）；`57f2cf2` 之後程式沒有變更
- 位置
  - `src/radar/collector/parsers/ptt.py:100`：`posts.created_at` 優先取文章標頭的「時間」，沒有上限，`2099` 年也接受
  - `src/radar/collector/scheduler.py:102-120`：`since = max(posts.created_at) - 10 分鐘`，不排除未來時間
  - `src/radar/collector/crawler.py:124-133`：第一頁最舊文章（檔名時間，PTT 產生）`<= since` 就停止往前翻
- 攻擊情境：被追蹤看板上任何一個 PTT 帳號發文後，用 PTT 的編輯功能把標頭「時間」改成 `Fri Dec 31 23:59:00 2099`（開發規格 7.28 A 的「自行決定」表本身就寫了「作者可改」）。下一次重爬把 `created_at = 2099-12-31` 寫進 PG，從此 Scheduler 對這個看板送出的每個列表任務都帶 `since ≈ 2099`，爬蟲讀完第一頁就停，不送續抓任務，也不記任何 WARNING／ERROR（流程看起來正常）
- 能拿到什麼：#180 要修的問題原樣回來，而且是永久、無聲的：停機、休眠、Kafka 停擺之後，第一頁以前的文章都不補（7.29 估計 Gossiping 停機一天約漏 790 篇）。對輿情雷達而言，等於攻擊者能選擇性讓某個看板在故障後的資料出現缺口，Dashboard 與熱度偵測看不到那段期間。只要文章不被刪就一直有效
- 為什麼不是 high：不洩漏資料、不取得權限；只有在停機或積壓超過一頁時才有實際缺口；不過門檻只是一個 PTT 帳號，所以評 medium
- 修法（擇一，建議第一個）
  - `latest_post_since` 改用 PTT 產生的檔名時間：`post_id` 已含 `M.<epoch>`，可以查該看板 `post_id` 的最大 epoch（或加一個不可被作者改的欄位）；7.28 A「列表用檔名時間」的比較基準也就一致了
  - 至少在查詢加 `Post.created_at <= now`（或在 parser 把標頭時間限制在「檔名時間 ± 1 天」，超出就退回檔名時間，同 #211 對推文時間的做法）
  - 補測試：PG 有一篇 `created_at` 在未來的文章時，`since` 不會晚於現在
- 備註：同一個標頭時間也被拿來推算推文年份（`_bounded_comment_time`），但只影響攻擊者自己那篇文章的推文，#211 已把未來時間設為 `None`，不另列

### L-1（low）已初始化過的 Grafana volume 不會跟著 `.env` 換掉 admin 密碼，`secret-check` 通過但實際密碼仍是 `change-me`

### L-3（low，第二次重審新增）`AE_TOKEN` 在同一個 job 跑過 PR 程式之後才使用，PR 內的程式或被污染的相依可以在 checkout 那一刻偷走它

- 第三次重審：`ci.yml` 只改了略過規則，步驟順序沒變，狀態照舊
- 位置：`.github/workflows/ci.yml:95-116`（`docker compose up`、`uv sync`、`make coverage`，執行 PR 的程式、測試、相依與 compose 設定）先跑，`:128-136` 才把 `secrets.AE_TOKEN` 交給 `actions/checkout`；`:119` 的註解說這個順序是為了讓測試、lint 不掃到工具本體
- 攻擊情境：一個開到 develop、從本 repo 分支發出的 PR，在測試期間留下背景程式（runner 在 job 結束前不清理孤兒程序；PR 的 compose 也能起一個 `pid: host` 的容器）。下一步 `actions/checkout` 的 node 程序帶著 `INPUT_TOKEN` 環境變數，同一個 `runner` 使用者可以從 `/proc/<pid>/environ` 讀到並外送。`persist-credentials: false` 只防「之後的步驟從 `.git/config` 讀」，防不了在使用當下讀取
- 誰能做到：能從本 repo 開分支的人（他本來就能改 PR 裡的 workflow 直接印出 secret，對他不算新風險）；真正新增的是「不用改 workflow、審查時不顯眼」的路徑：PR 帶進一個被污染的 PyPI 套件版本（`uv.lock` 升版）或 docker image，它在測試期間執行就能拿到 token
- 能拿到什麼：`Marcus778899/agent-engineering`（private）的唯讀程式碼，直到 token 到期或被撤銷。不能寫、碰不到本 repo、不含使用者資料，所以評 low
- 修法（擇一）
  - 把「Locate agent-engineering」「Checkout agent-engineering」兩步移到 integration job 最前面（`Checkout` 之後、任何 PR 程式執行之前）：checkout 結束 token 就從程序與 `.git/config` 消失；為了不被 lint、覆蓋率掃到，確認 `pyproject.toml` 的 ruff 排除與 `.coverage-exempt` 已含 `.claude/`（目前都有）
  - 或把覆蓋率閘門拆成獨立 job：integration job 上傳 `coverage-reports/`，閘門 job 只 checkout 本 repo（不執行 PR 程式）與工具，下載報告後跑閘門
- 同時建議（不需改程式）：`AE_TOKEN` 維持 fine-grained、單一 repo、Contents 唯讀、短到期；若工具 repo 改成 public 就刪掉這個 secret
