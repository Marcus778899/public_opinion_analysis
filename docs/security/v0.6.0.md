### 修法有沒有引入新問題

- **能不能讓別人的資料被刪**：不能。要讓 bot 對某個 chat 拿到 403，必須是那個 chat 封鎖或踢掉 bot，也就是該 chat 的擁有者或群組管理員自己的行為，結果和開發規格 7.21 的設計一致（推送路徑 `notify.py:93-95` 早就是這樣）。群組裡的任何管理員踢掉 bot 會刪掉整個群組的訂閱，這是預期行為
- **答錯 chat 的風險**：`answer_callback_query` 呼叫時沒有帶 `chat_id`，403 的例外裡 `chat_id` 會是 `None`，但處理時用的是 `callback.chat_id`（`:127-128`），不是例外裡的值，所以不會刪錯
- **log**：`forget_blocked_chat` 只記 chat_id，沒有 token 或訊息內容
- **還有沒有其他使用者可觸發的非暫時性例外**：重新走過指令與按鈕的所有分支。`parse_command`、`parse_callback` 格式錯誤回傳 `None`；`OVERVIEW`／`SUB` 檢查看板白名單；`TOGGLE` 有白名單；`MUTE`／`UNMUTE` 用 `split_post_id` 驗證並攔 `ValueError`（`callbacks.py:131-134`）；ClickHouse 查詢失敗攔 `QUERY_ERRORS`；`muted_posts.post_id` 是 `Text`，長度不會造成 `DataError`；訊息太長（例如不再通知清單很多）時 Telegram 回 400，會被攔下。沒有找到其他靠輸入就能讓指令 thread 結束的路徑
- **沒照做的部分**：上次修法第 2 點（`poll_commands` 對單筆 update 的非暫時性例外記錄後略過並推進 offset）沒有做，`poll_commands` 仍只攔 `TransientError`（`:175`）。上面確認過目前沒有使用者可觸發的路徑，所以不影響 H-1 的結論；但這是縱深防禦，列在 L-4 的修法裡一起處理

## 4. 本次新列的發現

### L-4（low）PG 斷線時指令 thread 結束，bot 在 PG 恢復前反覆重啟

architect review 指出 `forget_blocked_chat` 在 PG 斷線時會拋例外、讓指令 thread 結束。確認後判定為**舊有行為，不是 H-1 修法引入的**，而且影響範圍比 `forget_blocked_chat` 大：

**位置**
- `src/radar/bot/main.py:167`：`purge_muted` 在每輪迴圈開頭、`try` 之外執行，啟動後第一輪就會碰 PG
- `src/radar/bot/main.py:65`、`:79`：`reply_to`、`on_callback` 處理每一則指令和按鈕都會開 PG session
- `src/radar/bot/main.py:184`：`forget_blocked_chat`（本次新增的呼叫點）
- `src/radar/bot/main.py:175`：只攔 `TransientError`；SQLAlchemy 的 `OperationalError` 不是它的子類別，會讓 thread 結束 → `consumer.stop` → 服務結束 → docker `restart: unless-stopped` 重啟

**情境**：PG 重啟、維護或網路中斷時，bot 第一輪的 `purge_muted` 就會失敗，不論有沒有 403。在 PG 恢復前 bot 會一直重啟，指令和警示推送都停止；PG 恢復後自己就好了，未確認的 update 也會重送處理，不會遺失。

**嚴重度理由**：攻擊者沒辦法從外部讓 PG 斷線（PG 對外的 port 問題屬於 M-2／舊設定的範圍），所以不是可被未授權者利用的漏洞，影響只有可用性，而且會自己恢復 → low。`forget_blocked_chat` 只是多一個 PG 呼叫點，不會增加風險：403 那筆 update 在 PG 恢復後重送時會正常處理。

**修法**（建議開 backlog issue，不擋 v0.6.0）
- 在 `poll_commands` 把 `sqlalchemy.exc.OperationalError`／`DBAPIError` 當成暫時性錯誤，退避重試，`purge_muted` 也移進 `try`
- 對單筆 update 的其他非預期例外記 ERROR 後推進 `offset`（上次 H-1 修法第 2 點），讓未來新增的指令就算漏攔例外，也不會讓整個服務停掉
- 補測試，例如 `test_poll_commands_db_down_retries_without_exiting`
