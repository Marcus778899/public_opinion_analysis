### H-1（high）任何 Telegram 使用者都能讓 bot 進入重啟迴圈

**位置**
- `src/radar/bot/main.py:177-181`：`_send_reply` 只攔 `TelegramBadRequestError`
- `src/radar/bot/main.py:116-124`：按鈕回呼的 `answer_callback_query`／`edit_message_text` 也只攔 `TelegramBadRequestError`
- `src/radar/bot/main.py:165-174`：`poll_commands` 只攔 `TransientError`；`offset` 只存在記憶體，第 169 行在處理成功之後才前進
- `src/radar/bot/main.py:193-199`、`:253-254`：指令 thread 一出例外就停掉 alerts consumer，main 把例外往上拋，服務結束，由 docker（`restart: unless-stopped`）重啟
- `src/radar/bot/telegram.py:164-165`：403 會拋 `TelegramForbiddenError`，它不是 `TelegramBadRequestError` 的子類別

**攻擊情境**
1. 攻擊者：任何 Telegram 使用者。允許清單是空的時（`.env.example:110` 的預設值，見 M-1）不需要任何權限；有設清單時，清單內群組的任何成員都做得到
2. 做法：把 bot 拉進自己建的群組，送出 `/hot`（要查 ClickHouse，比較慢），接著馬上把 bot 踢出群組；私訊的話，送出 `/start` 後立刻封鎖 bot。用 userbot（MTProto）可以在同一秒內做完，不難搶贏時間差
3. bot 回覆時 Telegram 回 403 → 拋 `TelegramForbiddenError` → 指令 thread 結束 → alerts consumer 停止 → 服務結束
4. 重啟後 `offset` 是 `None`，`getUpdates` 又拿到那筆還沒確認的 update，再次 403，再次結束。Telegram 會保留未確認的 update 最多 24 小時，攻擊者隨時可以再來一次
5. 結果：在這段時間內，所有訂閱者都收不到熱度警示，所有指令也都失效（alerts 停在未 commit，修好後會一次推出大量過期警示）。不會洩漏資料，影響的是可用性；但攻擊者不需要授權，而且服務不會自己恢復，所以判為 high

**驗證**（只在本機用 fake client 跑，沒有連 Telegram）：用一個 `send_message` 一律拋 `TelegramForbiddenError` 的 fake 呼叫 `poll_commands` 兩次（模擬重啟）：

```
getUpdates offset= None
restart #0: poll_commands died with TelegramForbiddenError('chat 42 forbidden')
getUpdates offset= None
restart #1: poll_commands died with TelegramForbiddenError('chat 42 forbidden')
```

腳本在 scratchpad 的 `repro_403.py`，沒有提交。單元測試只涵蓋 alerts 推送路徑的 403（`tests/unit/bot/test_notify.py:154`），指令路徑和按鈕路徑都沒有測。開發規格 7.21 寫的是「403（使用者封鎖 bot）刪掉該 chat 的訂閱」，指令路徑沒有照著做。

**修法**
- `handle_update` 的回覆和回呼兩條路徑都要攔 `TelegramForbiddenError`：呼叫 `PreferenceRepository.forget(chat_id)` 並記 WARNING，和 `notify.py:93-95` 一樣
- `poll_commands` 對單筆 update 的非暫時性例外（`TransientError` 以外）要記錄後略過並推進 `offset`，一筆 update 不能讓整個服務停掉。DB 斷線之類的暫時性錯誤再另外分類重試
- 先補會失敗的測試，例如 `test_handle_update_forbidden_reply_forgets_chat`、`test_poll_commands_bad_update_advances_offset`

### M-1（medium）bot 允許清單預設不限制（fail open）

**位置**：`src/radar/common/settings.py:147-148`、`src/radar/bot/main.py:47-51`、`.env.example:109-110`；開發規格 7.21（第 933 行）寫「空字串為不限制」，設計文件 9.2（第 598 行）則寫「只回應允許清單內的 chat」

**攻擊情境**：bot 的 username 很容易被找到（警示會轉傳、群組裡看得到）。部署時沒設 `TELEGRAM_ALLOWED_CHAT_IDS` 的話，任何人都能：使用所有指令與按鈕；為自己的 chat 訂閱看板、收警示；不限次數觸發 `/hot`、看板概況這類要對 ClickHouse 跑 `FINAL` 的查詢（沒有限速，可以拖慢資源）；也能直接觸發 H-1。資料都以 Telegram 伺服器提供的 `chat.id` 區隔（`callbacks.py`、`repository.py` 每個查詢都用 `chat_id` 過濾，callback_data 不帶 chat_id），所以**看不到別人的訂閱或設定**。內容都是公開的 PTT 衍生資料，因此判為 medium。

**修法**：改成 fail closed，`TELEGRAM_ALLOWED_CHAT_IDS` 沒設時啟動失敗，或要求明確設定 `TELEGRAM_ALLOW_ALL=true`。這屬於權限相關的預設值（決策分級④），由 manager 決定要不要開 D-編號。同時把設計文件 9.2 和開發規格 7.21 的寫法統一。

### M-2（medium）Kafka 沒有驗證又對外開放；bot、heat 信任 topic 內容

**位置**
- `infra/docker-compose.yaml:57-58`、`:74-75`、`:91-92`：broker 的 EXTERNAL listener 綁 `0.0.0.0`，協定是 PLAINTEXT，沒有 SASL／ACL（`:8`）。這是舊設定，但本版新增的 `alerts → Telegram` 資料流讓它的影響變大
- `src/radar/common/schemas.py:194-206`：`Alert.unit_key`、`board`、`sample_post_ids` 只檢查是不是 `str`，沒有驗證 post_id 格式
- `src/radar/bot/views.py:75`、`:251-255`：產生畫面時 `split_post_id` 會拋 `ValueError`；`common/kafka/consumer.py:144-153` 只重試 `TransientError`，其他例外直接往上拋，訊息不會進 DLQ，offset 也不會 commit
- `src/radar/streaming/heat.py:381-383`：`board_of` 遇到格式錯誤的 post_id 會拋 `ValueError`，但只有 `DecodeError` 會被送進 DLQ（`:368-378`），其他例外讓服務停止

**攻擊情境**：和主機同一個網段的人（同一個 Wi-Fi 或 LAN；Docker Desktop 對外開的 port 不受 macOS 防火牆限制）連到 `<host>:9092`，不用帳密：
- 往 `alerts` 送一筆 schema 合法、但 `unit_key` 是 `x"><b>` 的訊息 → bot 產生畫面時拋 `ValueError` → 重啟後又讀到同一筆 → 一直重啟，所有警示都停擺（已在本機用 `Alert.model_validate` 加 `alert_screen` 確認：schema 接受這筆，產生畫面時會拋例外）
- 往 `alerts` 送合法的偽造警示 → 所有訂閱該看板的 chat 都會收到假的「推文暴增」。連結一律組成 `https://www.ptt.cc/...`，標題也都有 escape，所以不能拿來做釣魚連結，但警示本身的可信度會被破壞
- 往 `cdc.public.comments` 送 post_id 格式錯誤的 Avro → heat 一直重啟

需要網路位置相鄰，所以判為 medium。

**修法**
- 對外的 port 綁 `127.0.0.1`（和 api、clickhouse 的做法一樣），或改成 SASL＋ACL
- 在 `Alert`（以及 `CdcComment`）的 schema 用 `AfterValidator` 驗證 `unit_key`、`sample_post_ids`、`board` 的格式，讓壞資料在 decode 階段就進 DLQ
- 產生畫面時把 `ValueError` 當成單筆 Rejection 送進 DLQ，不要讓整個服務停掉（CLAUDE.md：壞資料送 `dlq`）

### M-3（medium）agent sandbox 放行 `docker compose *`

**位置**：`.claude/settings.json:8`（不經詢問就允許 `Bash(docker compose:*)`）、`:61`（`excludedCommands`，不受 sandbox 限制）；`infra/docker-compose.yaml:37` 的 `env_file: ../.env`

**攻擊情境**：agent 讀到的外部內容裡可能夾帶 prompt injection（PTT 文章內容、LLM 回應、issue 內文），一旦 agent 照著做，就能執行 `docker compose -f infra/docker-compose.yaml --env-file .env run --rm bot env`，在 sandbox 外印出 `.env` 裡所有的 token（Telegram、Groq、Gemini、OpenRouter、Slack、PG、ClickHouse），繞過 `Read(**/.env)` 的禁止規則；用 `run -v /:/host` 還能讀寫整台主機的檔案。CLAUDE.md 把 docker compose 列為「唯一在 sandbox 外的例外」，屬於刻意的取捨，但這個例外實際上讓 sandbox 不再能保護機密。這是開發環境的風險，和產品本身無關，所以判為 medium。

**修法**：把 `docker compose` 從 `allow` 移到 `ask`；或在 `guard_bash.py` 擋掉 `run`／`exec`／`-v`／`--volume`／`cp`，只放行 Makefile 用到的子指令（`up`、`down`、`ps`、`logs`、`build`）。

### L-1（low）所有 app 容器都拿到全部機密

**位置**：`infra/docker-compose.yaml:37`（`x-app.env_file: ../.env`，本版新增的 inference、heat、bot 都沿用）

**情境**：爬蟲會解析不受信任的 PTT HTML，但它的環境變數裡也有 `TELEGRAM_BOT_TOKEN` 和 LLM API key。只要任何一個服務被攻破（例如 parser 相依的漏洞），所有機密都會外洩。

**修法**：每個服務各用一份 `env_file`，或在 `environment` 只列需要的變數，做到最小權限。

### L-2（low）CI 下載的稽核工具沒有驗證完整性

**位置**：`.github/workflows/ci.yml:109`、`:113`

**情境**：版本有固定，但沒有比對 SHA-256。萬一 release 的檔案被換掉，就會在 CI 裡執行（權限是 `contents: read`，影響有限，但稽核結果本身可能被竄改）。

**修法**：同一個步驟裡用 `sha256sum -c` 比對寫死的雜湊值。

### L-3（low）`python3 -m http.server` 免詢問

**位置**：`.claude/settings.json:17`

**情境**：`http.server` 預設綁 `0.0.0.0`，在 repo 目錄執行時，同網段的人都能讀到 `data/`（爬下來的資料）、`models/`、`log/`。`.env` 有 sandbox 的讀取限制，不會被讀到。

**修法**：規則改成 `Bash(python3 -m http.server --bind 127.0.0.1:*)`，或改成需要詢問。

### 確認過、沒有問題的項目

- **chat_id 授權與他人資料**：`chat_id` 一律來自 Telegram 伺服器的 `message.chat.id`／`callback_query.message.chat.id`（`telegram.py:181-196`），callback_data 不帶 chat_id；每個 repository 查詢都用 `chat_id` 過濾。改 callback 參數只會影響自己的 chat。允許清單外的 chat 不會收到回應（`main.py:106`、`:113`）
- **callback_data 解析**：`parse_callback` 遇到版本、動作或格式不符都回傳 `None`；`OVERVIEW`／`SUB` 會檢查看板是否在 `enabled_boards`，`TOGGLE` 有白名單，`MUTE`／`UNMUTE` 用 `split_post_id` 驗證
- **HTML escape**：使用者輸入（指令參數）由 `commands.handle` 統一 escape；標題、看板名稱都經過 `escape()`；`href` 只會放 `post_url()`，它內部用 `split_post_id` 驗證字元，不可能出現引號
- **ClickHouse 注入**：bot 的查詢一律走伺服器端參數（`{name:Type}`）；陣列字面值先驗證過字元（`stats.py:132-144`）；`backfill_hash.update_statement` 內嵌的每個值都先用正規表示式驗證
- **token 處理**：Telegram token 只出現在 `base_url`；連線例外只保留類別名稱（`telegram.py:138-142`）；httpx2 的 `HTTP Request:` INFO log 寫在 `httpx2` logger 上，loggerhelper 不會接收（logger 不往上傳、root 沒有設定），所以不會寫進 log；LLM key 放在 header；設定都用 `SecretStr`
- **e2e**：`TELEGRAM_BOT_TOKEN: ''` 強制 e2e 不能推到真的 Telegram（`docker-compose.e2e.yaml`）
- **Migration**：3 個新的 Alembic migration 都沒有字串拼接；新表都標了 `debezium: no`

## 4. 測試覆蓋與爆炸半徑

- 有安全意義但沒有測試的路徑：指令和按鈕路徑的 403（H-1）、`Alert` 內容格式錯誤時 bot 的行為（M-2）、heat 收到 post_id 格式錯誤的事件
- `BatchConsumer` 遇到非暫時性例外就讓服務停止，這個行為所有 consumer（ingest、inference、label-stream、bot）都一樣。M-2 的修法如果改的是 consumer 而不是 handler，影響的不只 bot
